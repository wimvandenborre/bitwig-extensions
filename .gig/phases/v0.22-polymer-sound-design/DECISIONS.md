## 2026-03-13 — Discovery: Add device/discoverAll RPC method

**Decision:** Add a new `device/discoverAll` RPC method that automatically cycles through every parameter page on the currently selected device and returns the complete parameter map in a single response — page names, parameter names, default values, and displayed values for all pages.
**Rationale:** Currently requires N round-trips (selectPage → snapshot → selectPage → snapshot) to map a device. A single RPC call eliminates this friction and makes discovery a one-shot operation. The method is generic — works for Polymer, Wavetable, Phase-4, or any device.
**Alternatives considered:** Keep page-by-page workflow (too slow and error-prone for AI-driven discovery); add a bulk snapshot mode to session/snapshot (overcomplicates existing endpoint).
**Status:** ACTIVE
**ID:** D-22.1

## 2026-03-13 — Storage: Polymer parameter map as repo reference file

**Decision:** Store the Polymer parameter map as a JSON reference file at `gig-maestro/data/devices/polymer.json`. Structure: `{ deviceName, pageCount, pages: [{ index, name, tags, parameters: [{ index, name, defaultValue, defaultDisplayed }] }] }`. This file is generated by running `device/discoverAll` against a live Polymer instance and saving the output.
**Rationale:** A static reference file means the AI doesn't need a running Bitwig instance to know Polymer's layout. JSON is machine-readable and directly maps to the `macro/createSound` input format. Storing under `data/devices/` is generic — future devices (Wavetable, Phase-4, etc.) follow the same pattern.
**Alternatives considered:** Embed in system prompt (too verbose, hard to maintain); hardcode in Java (unnecessary coupling — this is AI reference data, not runtime logic); discover every session (wasteful, requires live Bitwig).
**Status:** ACTIVE
**ID:** D-22.2

## 2026-03-13 — Presets: Sound design recipes as JSON preset files

**Decision:** Create Polymer sound presets as JSON files under `gig-maestro/data/presets/polymer/` (e.g., `pluck.json`, `bass.json`, `lead.json`, `pad.json`, `keys.json`). Each preset contains: `{ name, description, device, pages: [...] }` — directly compatible with `macro/createSound` input format. Start with 5 core presets covering distinct timbres.
**Rationale:** JSON presets serve as both documentation and executable recipes. The AI can read a preset file and pass its `pages` array directly to `macro/createSound`. Separating presets from the parameter map keeps concerns clean — map = "what's available", preset = "what values produce this sound".
**Alternatives considered:** Put recipes in system prompt (already has generic ones — Polymer-specific values need to be validated against the real parameter map); single large file (harder to browse and maintain).
**Status:** ACTIVE
**ID:** D-22.3

## 2026-03-13 — Implementation: Scheduled page cycling with delay per page

**Decision:** `device/discoverAll` implementation cycles pages using `remoteControlsPage.selectedPageIndex().set(i)` with a 100ms delay between pages (matching existing `FLUSH_DELAY_MS`). Collects parameter state after each page switch. Returns the full map once all pages are read. First page is read immediately (current page), subsequent pages are scheduled.
**Rationale:** Bitwig needs one flush cycle to update parameter observers after a page switch. 100ms is the proven delay from `device/setParameters`. The method restores the original page index after scanning.
**Alternatives considered:** Read without delay (stale data from previous page); use longer delay (unnecessary, 100ms proven sufficient); parallel reads (not possible — single cursor).
**Status:** ACTIVE
**ID:** D-22.4

## 2026-03-13 — System prompt: Add device reference and preset loading guidance

**Decision:** Update the system prompt to document: (1) the `device/discoverAll` tool, (2) how to load device reference files from `data/devices/`, (3) how to load and apply preset files from `data/presets/`, and (4) a workflow for creating new presets by discovering a device, tweaking values, and saving the result. Keep generic — not Polymer-specific.
**Rationale:** The system prompt is the AI's instruction manual. Without guidance on the new data files and discovery tool, the AI won't use them. Generic framing supports future devices without prompt rewrites.
**Alternatives considered:** Polymer-specific prompt sections (won't scale); no prompt changes (AI won't discover the new capabilities).
**Status:** ACTIVE
**ID:** D-22.5
